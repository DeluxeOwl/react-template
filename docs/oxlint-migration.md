## 0. GOAL (agreed with the user on 2026-10-10, verbatim)

This is the restatement the user confirmed as correct before any work started. It is kept verbatim.

> **What I think the problem is**
>
> Today linting is split in two:
>
> - **ESLint** carries the heavy load: every workspace has an `eslint.config.ts` calling `createConfig` / `createReactConfig` (`packages/lint/src/index.ts`, `packages/lint/src/react.ts`). That resolves to **300 enabled rules** on `apps/web/app.tsx` (~**372** when you include test files), coming from ~18 plugins: @stylistic (71), @eslint-react (66), @typescript-eslint (48, many type-aware), sweepit (22), perfectionist (21), react-hooks (16), import-x, better-tailwindcss, you-might-not-need-an-effect, tanstack-query, unicorn, react-render-types, import-zod, unused-imports, react-refresh, ~70 vitest rules, plus your own `custom/*` rules.
> - **ESLint is also your TS/JS formatter** (@stylistic + `eslint --fix`, and VSCode uses the ESLint extension as default formatter).
> - **oxlint** runs alongside it, but on an old version (1.62; latest is 1.87) with JSON presets (`packages/lint/oxlint/*.json`), and ESLint needs the `eslint-plugin-oxlint` bridge to avoid double-reporting.
>
> So you're paying for two linters, two config systems, a slow gate, and a published `@deluxeowl/lint` package that drags ~20 third-party ESLint plugins along. Modern oxlint (TS config + ESLint-compatible JS plugins with fixes/tokens/scope analysis) makes it feasible to collapse almost all of this into oxlint — as code you own.
>
> **What I think your goals are**
>
> 1. Work on a branch.
> 2. **Upgrade oxlint** to latest and move the presets to `oxlint.config.ts`; verify nothing regresses before migrating anything.
> 3. **Migrate every effective ESLint rule** (including ones pulled in by presets) to oxlint, preferring: (a) a native oxlint rule when behavior/options match exactly; otherwise (b) your own oxlint JS-plugin rule, rewritten/ported from the upstream source; and only after a genuine attempt fails, (c) keep it in ESLint and document why.
> 4. **Parity is the bar**: same diagnostics and identical `--fix` output. **Formatting rules are the top priority**, since ESLint is your formatter today.
> 5. **The playground is the most important deliverable**: a fast, single-command, per-rule loop that runs ESLint (only that rule) vs oxlint (only the port) on the same corpus, diffs diagnostics and fixed output, so I can iterate until they match — then remove the rule from ESLint.
> 6. **Process**: I run that loop myself on representative rules (plain, type-aware, stylistic+autofix) until the workflow is solid; only then fan out with a SubagentWorkflow using strictly `agent-sol` agents, in small parallel batches with surgical changes.
> 7. I make the decisions; anything uncertain goes into the document for later review.
> 8. **Living document in `scratch/`** with full context: file:line references, per-rule status, parity evidence, decisions, open questions.
> 9. **End state**: ESLint removed, or reduced to a documented minimum.
>
> **How I'm interpreting the ambiguous parts**
>
> - **"Don't depend on third parties"** = the final config loads no third-party ESLint plugin (not even through oxlint's `jsPlugins`). Native oxlint rules and oxlint's own type-aware engine are fine since oxlint is the target tool. The upstream plugins remain only as dev deps of the parity harness until we're done; ported code keeps MIT attribution.
> - **Likely hard spots**: oxlint JS plugins can't see TypeScript types, so type-aware rules without a native oxlint equivalent (e.g. some `@typescript-eslint`, `react-render-types`, `@eslint-react/no-leaked-conditional-rendering`) may stay in ESLint; the react-hooks v7 rules run the React Compiler itself; better-tailwindcss needs Tailwind's engine (probably portable since `tailwindcss` is already your dep).
> - **Publishing**: I'll bump `@deluxeowl/lint` and update README/AGENTS.md/CI/lefthook/VSCode, but won't push tags, publish, or push the branch. I'll commit verified milestones locally with lowercase conventional messages.
> - **Branch**: you're already on `chore/oxlint-rule-parity` (same commit as `main`, 2df2d8c, clean tree) — I'll use that unless you want a new one.

### Phase 4 — parity harness (working)

See §7 for usage. Validation so far:

- Negative control: `@stylistic/semi` against a non-existent native rule → FAIL with the config error surfaced (an early version silently passed; fixed by treating "no JSON report" as a problem).
- **Upstream test harvesting** (`harness/harvest.ts`): runs the upstream plugin's own test files with every import replaced by a shim that only collects the `code` of each valid/invalid case (options and expected errors are ignored — ESLint with our options is the oracle). @stylistic v5.10.0: **8,686 cases** for the 71 rules (`harness/reports/harvest-stylistic.log`). These found every real divergence so far; the repo corpus alone passed 71/71.
- **Type-aware mode** (`harness/lib/sandbox.ts`): an rsync copy of the repo (node_modules and `packages/lint/dist` symlinked) so ESLint's project service and tsgolint both see every file on disk inside a real tsconfig. Mangled variants are skipped; `--fix` runs edit the sandbox only. Checked with `@typescript-eslint/no-floating-promises` vs native (68 files).
- **Directive renaming**: when the implementation runs under a different id (`upstream-*`, `*-js` aliases) the oxlint copy gets `eslint-disable` comments renamed to that id (and renamed back in the fixed output), mirroring what the migration does to the repo.
- Survey of every rule against oxlint's same-named native rule (`reports/survey-native.log`, 138 rules): 102 pass, **all vacuously** (0 diagnostics: the repo is clean and the mangler only produces formatting problems). Survey with upstream code inside oxlint (`reports/survey-upstream.log`, 266 rules): 253 pass. Both were run before F-012 and before harvesting, so they only show _runtime_ problems: type-aware rules need the sandbox, `vitest/no-focused-tests` native rejects the `fixable` option, upstream `@typescript-eslint/consistent-type-imports` needs parser services, upstream `import-x/no-unresolved` cannot resolve in the temp tree.
- Survey: **all 71 @stylistic rules PASS with `--impl upstream`** (upstream code loaded into oxlint as a JS plugin; 189 s for the batch). Caveats: (a) 27 rules had **0 diagnostics** in the corpus, so their pass is vacuous until cases exist; (b) oxlint needed up to **10 fix passes** (`key-spacing`), 3 (`indent-binary-ops`), 2 (`comma-dangle`) to reach ESLint's output (F-001). _Superseded by Phase 5 (harvested cases, vendored code, Node oracle)._
- **Together mode** (`parity.ts <rule> <rule>…` or `--plugin <prefix>`): all rules in one ESLint run and one oxlint run per file, so fixes of different rules compete in the same pass exactly as in `eslint --fix`. Reports per-rule divergence rows. Case files of different rules go to separate sub-directories (`__parity__/<rule-key>/`) because their names collide.
- Harness robustness fixes made while piloting: ESLint child runs under Node (F-012); an ESLint rule crash on a file is recorded (`ESLint crashes on N (excluded)`) instead of killing the child; oxlint "Error running JS plugin" diagnostics count as problems, not as parse errors; ESLint end positions past EOF are clamped like oxlint does (F-020); line mapping handles CR/LF/CRLF/U+2028/U+2029 (F-015).

### Phase 5 — solo pilot

#### @stylistic (71 rules, all fixable layout rules) — parity proven in the harness

What was done:

1. `vendor.ts @stylistic` copied the 71 enabled rules of `@stylistic/eslint-plugin` 5.10.0 and their 74-file import closure into `packages/lint/vendor/stylistic/` (MIT, LICENSE + README with provenance and patches). Runtime deps that remain: `@eslint-community/eslint-utils`, `@typescript-eslint/types`, `eslint-visitor-keys`, `espree`, `estraverse` (added to `packages/lint`; Q-004).

## 4. Decisions

**D-001 — Parity bar and third-party policy.** A rule counts as migrated when the harness shows the same diagnostics (spans; plus messages for ports) and byte-identical `--fix` output against ESLint on the real corpus, the mangled corpus and the rule's cases. The final config loads no third-party ESLint plugin, not even through `jsPlugins`. Upstream plugins stay installed (dev) only while the harness needs them.

**D-002 — oxlint 1.86.0, not 1.87.0.** `.npmrc` sets `min-release-age=7`; 1.87.0 was published 2026-10-05. Bump after 2026-10-12 and re-run the harness. Pinned exactly at the root; the published preset declares `oxlint >=1.86.0` as peer.

**D-003 — Presets are composed with `mergeOxlintConfigs`, not `extends`.** `extends` in `oxlint.config.ts` carries rules/plugins/overrides/categories only (F-003). The merge unions arrays, merges objects field by field (later wins), concatenates overrides.

**D-004 — New 1.86 rules that conflict with the codebase are off.** `one-var` (245 hits, conflicts with the one-declaration-per-line style), `prefer-named-capture-group` and `require-unicode-regexp` (would rewrite every regex; `u` changes semantics), `typescript/method-signature-style` (ESLint deliberately disables the same rule), `unicorn/max-nested-calls` (flags idiomatic nested zod schemas). `no-unused-vars` gets the ESLint preset's options so a bare `_` stays allowed. See comments at `packages/lint/src/oxlint/typescript.ts:108-177`. _Review item Q-001._ _Superseded by D-023: all but `one-var` are on since `706383d`._

**D-005 — Freeze the bridge instead of using eslint-plugin-oxlint.** With the presets passed as an object, the bridge (1.86) also switched off 7 core/TS rules and 12 react-hooks rules in ESLint (it now sees categories; before, `extends` hid them). That would have moved rules to oxlint without parity proof. `packages/lint/src/handled-by-oxlint.ts` is the exact output of eslint-plugin-oxlint 1.62 on the old presets (121 base + 57 React rules). The frozen list is not touched by the migration; migrated rules go through D-014. When _every_ rule of a plugin moves, the plugin and its dependency leave the ESLint presets instead (done for `@stylistic`).

**D-006 — The harness lives in `scratch/` (not committed).** It depends on ESLint + every upstream plugin and is only useful while migrating. The lasting artefacts (ported rules + their tests) go into `packages/lint`. _Review item Q-002._

**D-007 — Ported rules keep their upstream ids when oxlint allows it.** Our JS plugins are registered with the upstream prefix (`@stylistic`, `perfectionist`, `sweepit`, `@eslint-react`, `custom`, `@tanstack/query`, …), so existing `eslint-disable` comments and docs keep working. oxlint reserves `vitest`, `react-hooks`, `unicorn`, `import-x`, `@typescript-eslint`, `jest`, `import`, `eslint`, `react`, `jsx-a11y`, `node` (F-006); ports of rules from those plugins use `<name>-js` (e.g. `vitest-js/…`) and their disable comments get rewritten. _Review item Q-003._

**D-008 — Ports vendor the upstream implementation.** "Port" = copy the upstream rule source (MIT, attribution kept) into `packages/lint/vendor/<plugin>/` (generated by `vendor.ts`; compiled upstream JS, so it stays outside `src/`), trimmed to the rules we use, then fix whatever oxlint needs through patches listed in `vendor.ts` — never by hand. Rewriting from scratch would only add risk to a byte-identical target. Small generic runtime helpers the vendored code imports (e.g. `espree` tokenizer, `eslint-visitor-keys`, `@eslint-community/eslint-utils`) may stay as dependencies; ESLint plugins and ESLint itself may not. _Review item Q-004._

**D-009 — Fix order compatibility layer for vendored rules.** `packages/lint/vendor/_compat/report-order.js` wraps every vendored rule: reports are queued and emitted at the end of the file sorted by (line, column, report order) like ESLint's problems; a report whose fix range equals the range of an earlier report's fix loses its fix (ESLint could never apply it in that pass — it would overlap the first); fixes are computed at report time and merged like ESLint's `mergeFixes`. `vendor.ts` registers rules in the ESLint config's order (F-017). Without it, 13 of 386 mangled files ended with different formatting in together mode (F-016). Limits: only covers our JS plugins — a native oxlint rule's fix with exactly the same range as a JS rule's fix is still an arbitrary tie (none seen yet); a rule crash drops the file's queued reports (oxlint drops them anyway, F-021). Worth an upstream issue: a stable sort keyed on (fix span, line, column) in `oxc_linter/src/fixer/mod.rs` would make the layer unnecessary. _Amended (react-misc):_ the wrapper now runs ESLint's whole fix selection (`source-code-fixer.js`) over the vendored rules' fixes — sort by range (start, then end), stable over problem order; skip a fix that starts at or before the end of the last applied one — and removes the fix (not the diagnostic) from every report ESLint would skip in this pass. oxlint then only receives fixes that don't overlap. Before, only fixes with exactly the same range were handled; the result is the same as long as oxlint sorts by the full span (it does, F-016), but the wrapper no longer depends on that.
_Amended in Phase 6 (perfectionist):_ (1) a later fix is only dropped when its range is taken by an earlier fix with **different** text (identical fixes are harmless — perfectionist attaches the same group fix to every report of a group); (2) the wrapper applies disable directives itself with ESLint's semantics (`sourceCode.getDisableDirectives()` + the algorithm of ESLint's `apply-disable-directives.js`, keyed on `context.id`) and drops suppressed reports before oxlint sees them — so a suppressed report no longer "takes" a range (ESLint resolves conflicts after suppression: `perfectionist/sort-array-includes` case with `/* eslint-disable */` inside the array got no fix at all before), and F-030 is gone for vendored rules. oxlint's own directive pass still runs afterwards (F-028 remains: where oxlint suppresses more, nothing can be done from a plugin).

**D-011 — `oxlint-fix` loops `oxlint --fix` (≤ 10 rounds) for the CLI.** Without it `lint:oxlint` would stop half-way on files whose fixes depend on each other and still exit 0 (F-001, F-022), so neither "byte-identical to `eslint --fix`" nor the pre-push gate would hold. A round that changes no file (sha1 over `git ls-files --cached --others --exclude-standard` JS/TS/Vue/Svelte/Astro files under cwd) ends the loop with that round's report; after 10 changing rounds it lints once more without fixing, like ESLint. Outside a git work tree every round runs. Global rounds equal ESLint's per-file passes because each file's fixes only depend on that file. Shipped from `@deluxeowl/lint` as `runOxlintFix` + the `oxlint-fix` bin. The bin is committed plain JS that imports `dist` (F-023). Editors still get one round per save. _Review item Q-006._

**D-012 — Vendored code ships in the published package.** `files` now lists `vendor` (and `bin`); the stylistic preset points at `vendor/stylistic/index.js` relative to the built module, so consumers need nothing else. Vendored code is excluded from our own lint/format/dup/deadcode tools; its runtime helper deps are regular `dependencies` of `@deluxeowl/lint`.

**D-013 — oxlint type-aware mode is on; every type-aware rule is listed explicitly.** `packages/lint/src/oxlint/type-aware.ts` sets `options.typeAware: true` and lists all 60 type-aware rules of oxlint 1.86: `"off"` unless migrated with parity. ## 5. Verified facts about oxlint 1.86 (F-xxx)

- **F-001 — `oxlint --fix` applies one pass; ESLint loops up to 10.** Demo plugin that shortens `xxxxx` by one char per fix: oxlint → `xxxx`, ESLint → `x`. Overlapping fixes in a pass: both keep the first. Consequence: byte-identical formatting needs either fixers that converge in one pass or running `oxlint --fix` until stable. The harness loops (max 10) and reports the passes needed.
- **F-002 — JS plugins run upstream ESLint rules faithfully.** All 71 @stylistic rules produce identical diagnostics and fixes to ESLint on our corpus (vacuous for 27 of them so far).
- **F-003 — `extends` in `oxlint.config.ts` ignores env, settings, globals, ignorePatterns.**
- **F-004 — `--print-config` hides options of rules that come from `extends`,** and omits some active plugins from `plugins`. Verified at runtime: `max-params` with max 2 fired through `extends` while print-config showed bare `"deny"`.
- **F-005 — JSON output spans are UTF-8 byte offsets; `column` is byte-based.** ESLint uses UTF-16 columns. The harness converts.
- **F-006 — Reserved JS plugin names:** vitest, react-hooks, unicorn, import-x, @typescript-eslint, jest, import, eslint, react, jsx-a11y, node (tested). Allowed: @stylistic, @eslint-react, perfectionist, @tanstack/query, react-refresh, custom, n.
- **F-007 — typescript-eslint's project service is process-global** (ESLint side): one process per workspace.
- **F-008 — An unknown rule in the config is a hard error** ("Failed to parse oxlint configuration file", exit 1, no JSON report).
- **F-009 — Native formatting rules don't exist** (no semi/quotes/indent/spacing/comma rules in the 871-rule catalog), so every @stylistic rule is a JS-plugin port.
- **F-010 — Node loads `oxlint.config.ts` and JS plugins** (Node ≥ 22.18; we have 25.3). Extensionless relative imports fail under Node (worked under Bun) → source uses explicit `.ts` imports + `rewriteRelativeImportExtensions`.
- **F-011 — 1.86 `unicorn/prefer-export-from` also flags `export const X = imported`** (1.62 did not). No hit in the codebase; test fixtures adjusted.
- **F-012 — Bun (JavaScriptCore) mis-evaluates some regexes; ESLint must run under Node.** `/^(?=( +|\t+))\1(?:\t| )/u` (used by `@stylistic/no-mixed-spaces-and-tabs`) does not match `"\t var a"` when the string came from `JSON.parse` of text containing a non-Latin-1 character (Bun 1.3.3; Node matches). The harness's ESLint child got its files through a JSON payload, so the _oracle_ was wrong (14 phantom divergences). The repo's `eslint` bin and the VS Code extension run under Node, and so do oxlint JS plugins, so the child now runs under Node (`harness/lib/eslint-runner.ts`). Surveys run before this fix were re-run.
- **F-013 — oxc does not decode HTML entities in JSX string values.** `<a b='&quot;' />`: typescript-estree gives the attribute Literal `value` `"`; oxc gives `&quot;`. Same for `JSXText.value` (`&lt;hi&gt;` stays encoded). `raw` is the same in both. Rules that read `.value` of JSX strings need `jsxStringValue(node)` from `packages/lint/vendor/_compat/jsx-entities.js` (decodes `raw` exactly like typescript-estree's `unescapeStringLiteralText`). Affected so far: `@stylistic/jsx-quotes` (patched). Worth reporting upstream to oxc.
- **F-014 — oxc rejects some code typescript-estree accepts**: `with` statements (modules are strict) and `namespace` declarations inside blocks (TS1235). Only seen in harvested upstream test snippets — such code is invalid TypeScript anyway. The harness excludes cases oxc cannot parse and lists them in the report (`corpus.oxcRejected`).
- **F-015 — Line counting.** ESLint ends lines at `\r\n`, `\r`, `\n`, U+2028 and U+2029. The harness converts ESLint line/column to offsets the same way (an upstream snippet with U+2028 inside a comment exposed this).
- **F-016 — oxlint breaks ties between same-range fixes arbitrarily.** `Fixer::fix` sorts with `sort_unstable_by_key(|m| m.fixes.span())` (oxc tag `oxlint_v1.86.0`, `crates/oxc_linter/src/fixer/mod.rs:361`) and then skips fixes that start at or before the previous fix's end (same rule as ESLint). ESLint first sorts problems by (line, column) (`linter.js:1305`) and then fixes by range with a stable sort (`source-code-fixer.js:124`), so the first problem in (line, column, report) order wins. Example: `}   ,` — `no-multi-spaces` (col 13) wants `" "`, `comma-spacing` (col 16) wants `""`; ESLint applies `" "`, oxlint applied `""`. Small files happen to keep report order (insertion sort below 20 elements), large ones do not.
- **F-017 — Rule order within one AST event:** ESLint calls listeners in the order of the config's `rules`; oxlint in the order of the plugin's `rules` object (registration order); the config order is ignored. Verified both ways with a two-rule test plugin (`foo` → `foo_a`/`foo_b`).

- **F-019 — oxlint's rule `context` is non-extensible with a read-only own `report`;** a `Proxy` cannot override it (proxy invariant), but `Object.create(context, { report })` works — the same thing oxlint's `context.extend()` does. Other members are getters on a shared prototype that read per-file module state, not `this`.

- **F-022 — `oxlint --fix` exits 0 when its fixes create problems it does not report.** It reports "only unfixed issues" from the pre-fix lint: `{ a: 1, bb: 2, ccc: 3 }` spread over lines → one `--fix` aligns values and moves `ccc` to a new unindented line, prints nothing, exits 0; the next `oxlint` reports `@stylistic(indent)`. - **F-023 — Bun workspace bins.** (a) `bun install` links a workspace package's bin only if the target file exists at install time, so a bin pointing into `dist/` (built by postinstall/CI after install) is never linked on a fresh checkout → the bin is committed plain JS. - **F-032 — harness: typed runs lost `packages/lint` files once a migration was integrated (fixed).** The typed sandbox (`harness/lib/sandbox.ts`) is the oracle tree with today's corpus files written over it — including `packages/lint/src/**`, which `packages/lint/eslint.config.ts` imports as its own config. - **F-034 — ESLint 10 stops fixing a file when its fixes go in circles.** `verifyAndFix` (`eslint/lib/linter/linter.js:1585`, eslint 10.3) ends the pass loop when a pass produces the text the file had two passes earlier, and warns `Circular fixes detected while fixing <file>. It is likely that you have conflicting rules in your configuration.` Found by the react-misc together run: `@tanstack/query/infinite-query-property-order` wants `queryFn` before `getNextPageParam`, `perfectionist/sort-objects` wants them sorted, so their fixes alternate. ## 7. The playground — how to run the per-rule loop

```sh
# one rule, auto-selected implementation (our port > native candidate > upstream-in-oxlint)
bun scratch/oxlint-migration/harness/parity.ts @stylistic/key-spacing

# force the implementation
bun scratch/oxlint-migration/harness/parity.ts @stylistic/key-spacing --impl upstream
bun scratch/oxlint-migration/harness/parity.ts @typescript-eslint/no-explicit-any --impl native:typescript/no-explicit-any

# narrow / widen the corpus
bun scratch/oxlint-migration/harness/parity.ts @stylistic/indent --files apps/web --variants 6 --prob 0.3 --show 3

# many rules
bun scratch/oxlint-migration/harness/batch.ts --plugin @stylistic --impl upstream --concurrency 4
```

What one run does:

1. **Corpus** — real tracked files of the six workspaces (68), N mangled variants per file (seeded, parse-checked; whitespace, line breaks, quotes, trailing commas, semicolons, member delimiters), and `cases/<rule>/*` (virtual path via a `// parity-path: apps/web/x.tsx` first line).
2. **ESLint** — the real workspace config, only the target rule (`ruleFilter`), unused-directive reports off, no type info unless `--type-aware`/the rule needs it. One child per workspace, in parallel. Collects diagnostics and `--fix` output (ESLint's own 10-pass loop), plus the rule's options and settings **for each file**.
3. **oxlint** — temp tree mirroring repo paths; a generated config per distinct (options, settings) group enabling only the implementation under test. Diagnostics run, then `--fix` repeated until stable (≤ 20, D-019; a file that repeats its state from two passes before leaves the loop, like ESLint's circular-fix check).
4. **Compare** — spans (UTF-16), messages (ports/upstream only), fixed output byte for byte. Prints a summary, the first divergences with code frames / unified diffs, and writes `reports/<rule>.<impl>.json`. Exit 0 = PASS.

Speed: ~3–5 s per rule on 200 files.
